## 🐞 Testing vs. Debugging

- **Testing (Validation):** The process of running a program to find out if it works as expected. "Does it break?"
- **Debugging:** The process of finding the root cause of a bug and fixing it. "Why did it break, and how do I fix it?"

### Defensive Programming
The best way to debug is to prevent bugs in the first place! 
- Write clear function specifications (docstrings).
- Keep functions small and modular (Decomposition).
- Validate inputs before doing calculations.
- Use assertions to verify assumptions.

### Before Testing
Before testing, make sure:
- Syntax errors are removed.
- The program runs.
- Expected outputs are known.
- Test cases are prepared.

### Types of Testing
1. **Unit Testing:** Tests individual functions separately.
2. **Regression Testing:** Ensures previously fixed bugs do not return. Whenever a bug is fixed, add a test case for it.
3. **Integration Testing:** Tests whether all modules work together correctly (e.g., `Input → Function A → Function B → Output`).

---

## 🧪 Testing Approaches

When testing your code, you should intentionally try to break it by passing unusual inputs.

### 1. Black Box Testing
Testing a function **without looking at its code**. You only care about the inputs and outputs based on the docstring specification.

For a function `def sqrt(x, eps):`, you would test:

| Test Case | x | epsilon |
|-----------|---:|---------:|
| Boundary | 0 | 0.0001 |
| Perfect square | 25 | 0.0001 |
| Less than 1 | 0.05 | 0.0001 |
| Irrational root | 2 | 0.0001 |
| Very large value | 2**64 | 0.0001 |
| Very small value | 1/(2**64) | 0.0001 |

Useful for finding missing or incorrect behavior.

### 2. Glass Box (White Box) Testing
Testing a function **by examining the code** to ensure every possible path executes at least once.

```python
def absolute(x):
    if x < -1:
        return -x
    else:
        return x
```
> [!WARNING]
> If you only test `x = -2` and `x = 2`, you will achieve 100% path coverage, but you will miss the bug! If `x = -1`, the function returns `-1` (incorrect). Always test the boundaries of `if` statements!

## 💥 Common Error Types

1. **SyntaxError:** You typed invalid Python syntax (e.g., missing a parenthesis `)`). The code won't even run.
2. **Runtime Exceptions:** The code is syntactically valid but fails during execution (e.g., dividing by zero).
3. **Logic Errors:** The code runs perfectly, but the output is wrong. These are the hardest to fix.
   - **Tips:** Think before writing more code, draw diagrams, explain your code aloud (**Rubber Duck Debugging**), and test with simple inputs.

### The Debugging Process
1. Observe the unexpected result.
2. Form a hypothesis.
3. Test the hypothesis.
4. Fix the bug.
5. Test again.

Repeat until the program works correctly.

### Common Runtime Exceptions
| Exception | Cause | Example |
| :--- | :--- | :--- |
| `IndexError` | Trying to access an index that doesn't exist | `L = [1, 2]; print(L[5])` |
| `TypeError` | Performing operations on incompatible types | `"5" / 2` |
| `ValueError` | Passing an invalid value to a function | `int("apple")` |
| `NameError` | Using a variable before it is defined | `print(unknown_var)` |
| `KeyError` | Accessing a non-existent key in a dictionary | `d = {}; print(d["missing"])` |
| `AttributeError` | Accessing an attribute/method that doesn't exist | `import math; print(math.PI)` |
| `ModuleNotFoundError`| Importing a module that is not installed or misspelled | `import maths` |
| `ImportError` | Importing a specific attribute/function that doesn't exist in module | `from math import power` |
| `ZeroDivisionError`| Dividing a number by zero | `10 / 0` |

## 🛡️ Handling Exceptions: `try...except`

Instead of letting a runtime exception crash your program, you can handle it using a `try...except` block.

```python
try:
    num = int(input("Enter a number: "))
    print(100 / num)
except ValueError:
    print("Error: That was not a valid number!")
except ZeroDivisionError:
    print("Error: You cannot divide by zero!")
except Exception:
    print("An unknown error occurred.")
```

### The `else` and `finally` Blocks
- **`else`:** Runs *only* if no exceptions occurred in the `try` block.
- **`finally`:** Runs *always*, regardless of whether an exception occurred. Usually used for cleanup (like closing files).

```python
try:
    x = int("10")
except ValueError:
    print("Failed")
else:
    print("Success!")
finally:
    print("Always prints.")
```

## 🚀 Raising Exceptions: `raise`

You can **deliberately trigger an exception** using the `raise` statement. This is used to signal that something is wrong — typically to enforce a function's contract.

```python
def set_age(age):
    if age < 0 or age > 150:
        raise ValueError(f"Invalid age: {age}. Must be between 0 and 150.")
    return age

try:
    set_age(-5)
except ValueError as e:
    print(f"Caught error: {e}")
```

**Output:**
```text
Caught error: Invalid age: -5. Must be between 0 and 150.
```

> [!IMPORTANT]
> **`raise` vs `assert`**:
> | | `raise` | `assert` |
> | :--- | :--- | :--- |
> | **Use for** | User-facing input validation, API contracts | Internal developer sanity checks |
> | **Exception type** | Any exception (`ValueError`, `TypeError`, etc.) | Always `AssertionError` |
> | **Can be disabled?** | No | Yes (`python -O` flag disables assertions) |
> | **Caught by `except`?** | Yes | Yes, but only `AssertionError` |

### 🏗️ Practice Problem: `pairwise_div`

Write a function that divides elements of two lists pairwise.
```python
def pairwise_div(Lnum, Ldenom):
    """
    Lnum and Ldenom are non-empty lists of equal length.
    Returns a new list containing the pairwise division.
    Raises ValueError if any denominator is 0.
    """
    result = []
    for i in range(len(Lnum)):
        if Ldenom[i] == 0:
            raise ValueError("Denominator cannot be zero.")
        result.append(Lnum[i] / Ldenom[i])
    return result

print(pairwise_div([4, 5, 6], [1, 2, 3])) # [4.0, 2.5, 2.0]
# print(pairwise_div([4, 5, 6], [1, 0, 3])) # ValueError: Denominator cannot be zero.
```

## 🛑 Assertions

An `assert` statement is a defensive programming tool used to verify that a condition is True. If it is False, the program immediately crashes with an `AssertionError`.

**Syntax:** `assert condition, "Error message"`

```python
def calculate_discount(price, discount):
    assert price >= 0, "Price cannot be negative!"
    assert 0 <= discount <= 1, "Discount must be between 0 and 100%"
    
    return price * (1 - discount)

# calculate_discount(-50, 0.2) # Crashes: AssertionError: Price cannot be negative!
```

> [!TIP]
> Use `try...except` to handle user input errors gracefully. Use `assert` to catch programmer errors and validate assumptions during development.

### Assertions vs `if`
- **`if`** → used to **handle** a condition (e.g., branching based on user input).
- **`assert`** → used to **verify** an assumption (e.g., variables must not be negative).

> [!NOTE]
> The optional message after the comma is shown to the developer when the assertion fails:
> ```python
> assert price >= 0, "Price cannot be negative!"
> # If price = -5, raises: AssertionError: Price cannot be negative!
> assert False, "This code should never be reached!"
> # Always raises: AssertionError: This code should never be reached!
> ```

### Assertions vs Exceptions
| Assertions | Exceptions |
| :--- | :--- |
| Used to check assumptions | Used to handle unexpected conditions |
| Mainly useful for detecting bugs | Mainly useful for handling errors |
| Failure raises `AssertionError` | Can raise different exception types |
| Useful for enforcing program contracts | Useful for handling bad user input |

### Important Idea: Fail Early
Assertions help us **fail early**. Instead of allowing an invalid value to travel through several functions and cause a confusing error later, an assertion detects it immediately at the source.

## 🔍 Debugging Tools & Techniques

### Using Print Statements
One of the simplest and most effective debugging tools. Useful places to print:
- Function entry
- Input parameters
- Intermediate variables
- Function return values

### Bisection Debugging
When a program has a logic error, use **Bisection Debugging** with `print()` statements.

1. Put a `print()` statement halfway through your code to inspect variables.
2. If the values are correct, the bug is in the *second half* of the code.
3. If the values are wrong, the bug is in the *first half* of the code.
4. Repeat (just like binary search!) until you find the exact line causing the issue.

### Best Practices
- Test small functions first.
- Test normal, boundary, and invalid inputs.
- Keep functions short and modular.
- Add regression tests after fixing bugs.
- Fix one bug at a time.

## Advanced Practice & Exam-Style Questions

### Question 1: The `NameError` Trap 🐛 (Debugging)

What is the output of this code?
```python
try:
    result = 10 / 0
except ZeroDivisionError:
    print("Failed to divide.")
    print("Result was:", result)
```

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### ✅ Solution
It prints `"Failed to divide."` and then crashes with a `NameError: name 'result' is not defined`.

#### 🔍 Explanation
When `10 / 0` triggers a `ZeroDivisionError`, the assignment to the variable `result` **never happens**. Therefore, when the `except` block tries to print `result`, the variable doesn't exist yet! 
**Fix:** Always initialize variables *before* the `try` block if you plan to use them in the `except` or `finally` blocks.
</details>

### Question 2: Exception Hierarchy Order ⭐⭐

What does this code output?
```python
try:
    print(5 / 0)
except Exception:
    print("A")
except ZeroDivisionError:
    print("B")
```

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### ✅ Solution
```text
A
```

#### 🔍 Explanation
Python checks `except` blocks from top to bottom. `Exception` is the base class for all exceptions, so it catches the `ZeroDivisionError` first. Always put specific exceptions (like `ZeroDivisionError`) *before* general exceptions.
</details>

### Question 3: The `finally` Override 💼 (Advanced)

What does this function return?
```python
def test():
    try:
        return 1
    finally:
        return 2

print(test())
```

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### ✅ Solution
```text
2
```

#### 🔍 Explanation
The `finally` block **always runs**, even if the `try` block hits a `return`, `break`, or `continue`. When the `try` block tries to return `1`, Python pauses, executes the `finally` block, and since the `finally` block returns `2`, it **overrides** the original return value!
</details>

### Question 4: `raise` vs `assert` 🧠 (HOTS)

What is the difference between `raise ValueError("Oops")` and `assert x > 0, "Oops"`?

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### 🔍 Explanation

- `assert` only triggers an `AssertionError`, and it only happens if the boolean condition evaluates to `False`. Assertions are meant for internal sanity checks by the developer to ensure the code is operating correctly.

### Question 4.1: The `assert` Statement 💡 (Concept Check)

What exception does `assert False, "Should not be here"` raise, and when would you use it?

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### ✅ Solution
It raises `AssertionError: Should not be here`.

#### 🔍 Explanation
`assert False` unconditionally fails because the condition is always `False`. This is useful to mark code paths that should **never be reached** — for example, the final `else` branch of a chain of `if/elif` conditions that supposedly handles all cases:
```python
def classify(grade):
    if grade == 'A':
        return "Excellent"
    elif grade == 'B':
        return "Good"
    else:
        assert False, f"Unexpected grade: {grade}"  # Programmer error!
```
This pattern is called a **"defensive assert"** and makes bugs visible immediately rather than silently returning the wrong result.
</details>

### Question 5: Syntax vs. Runtime vs. Logic 🐛 (Concept Check)

A developer writes a program to calculate the area of a circle (`pi * r^2`). They write `area = 3.14 * r * 2`. The program runs without crashing but gives the wrong area. What kind of error is this?

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### ✅ Solution
A **Logic Error** (or Semantic Error).

#### 🔍 Explanation
- **Syntax Error**: The code wouldn't even run (e.g., `area = 3.14 * r * * 2`).
- **Runtime Error**: The code runs but crashes during execution (e.g., if `r` was a string `"five"`, causing a `TypeError`).
- **Logic Error**: The code runs perfectly and produces a result, but the mathematical formula is wrong (`r * 2` instead of `r ** 2`). These are the hardest bugs to track down because the computer doesn't give you an error message!
</details>

### Question 6: Black-box vs. Glass-box Testing 📦 (Advanced)

You are tasked with testing a function `def is_prime(n):`. 
1. If you test it with `n = -5, 0, 1, 2, 9, 13`, without ever looking at the source code, what kind of testing is this?
2. If you open the source code, see a loop `for i in range(2, n):`, and realize you need to test `n=2` to ensure the loop behaves correctly when `start == stop`, what kind of testing is this?

<details>
<summary><b>💡 Click to Reveal Solution & Explanation</b></summary>

#### ✅ Solution
1. **Black-box Testing**
2. **Glass-box (or White-box) Testing**

#### 🔍 Explanation
- **Black-box testing** only relies on the specification (the docstring). You feed it inputs and check outputs.
- **Glass-box testing** relies on the implementation details. You design test cases specifically to ensure every `if` statement branch, loop, and exception path is executed at least once (path coverage).
</details>

## 🏗️ Real-World Challenge: Fix the Buggy Calculator

### 📌 Problem Statement
A junior developer wrote a command-line calculator that takes a list of strings representing math operations (e.g., `["10", "/", "2"]`) and calculates the total. However, the program crashes frequently and sometimes produces the wrong answer! 

Your job is to debug and fix it using `try...except`, `assert`, and your knowledge of logic errors.

### 🐛 The Buggy Code

```python
def process_calculations(operations):
    total = 0
    current_num = 0
    operator = "+"

    for item in operations:
        if item == "+" or item == "-" or item == "/":
            operator = item
        else:
            current_num = int(item)
            
            if operator == "+":
                total += current_num
            elif operator == "-":
                total -= current_num
            elif operator == "/":
                total /= current_num
                
    return total

# Test Cases:
# print(process_calculations(["10", "/", "0"])) # Crashes!
# print(process_calculations(["10", "+", "apple"])) # Crashes!
# print(process_calculations(["10", "-", "5", "-", "5"])) # Should be 0.
```

### 🧠 Systematic Debugging Framework

<details>
<summary><b>1. Hypothesis Generation & Bisection Debugging</b></summary>

1. **Crash 1 (`["10", "/", "0"]`)**: Division by zero! We need a `try...except ZeroDivisionError` block.
2. **Crash 2 (`["10", "+", "apple"]`)**: `"apple"` cannot be cast to an integer. We need a `try...except ValueError` block.
3. **Logic Error (`["10", "-", "5", "-", "5"]`)**: Wait, the buggy code sets `total = 0` initially. If the first number is `10` and the operator is `+`, it does `0 + 10 = 10`. Then `- 5` gives `5`. Then `- 5` gives `0`. This one actually works for the buggy code! But what if the list starts with multiplication? The buggy code doesn't support multiplication.
</details>

<details>
<summary><b>2. The Fixed Implementation</b></summary>

```python
def process_calculations(operations):
    assert len(operations) > 0, "Operations list cannot be empty!"
    
    total = 0
    operator = "+"

    for item in operations:
        if item in ["+", "-", "/", "*"]:
            operator = item
        else:
            try:
                current_num = float(item) # Using float to support decimals!
                
                if operator == "+":
                    total += current_num
                elif operator == "-":
                    total -= current_num
                elif operator == "*":
                    total *= current_num
                elif operator == "/":
                    total /= current_num
                    
            except ValueError:
                print(f"Warning: Skipping invalid number '{item}'")
            except ZeroDivisionError:
                print(f"Warning: Tried to divide by zero! Skipping operation.")

    return total

print("Test 1:", process_calculations(["10", "/", "0"])) 
# Warning: Tried to divide by zero! Skipping operation. -> Output: 10.0

print("Test 2:", process_calculations(["10", "+", "apple"])) 
# Warning: Skipping invalid number 'apple' -> Output: 10.0
```
</details>

## 🔑 Key Takeaways

| Concept | Key Point |
| :--- | :--- |
| **Black Box vs Glass Box** | Black box tests based on specs; Glass box tests all code paths. |
| **`try...except`** | Catches runtime errors (exceptions) so your program doesn't crash. |
| **`raise`** | Deliberately triggers a specific exception to enforce contracts. |
| **Exceptions vs Assertions** | Use exceptions for expected user/runtime errors. Use `assert` to catch impossible developer bugs. |
| **`else` and `finally`** | `else` runs if no error occurred. `finally` runs no matter what. |
| **Bisection Debugging** | Use `print()` statements to cut the search space in half until you find the broken line. |
